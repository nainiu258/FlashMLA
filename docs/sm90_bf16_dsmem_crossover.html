SM90 BF16 Sparse Prefill：DSMEM Crossover

实验性实现：让处理同一请求、不同 64-head 半区的两个 CTA 组成 cluster，分摊 selected-KV 的 global load，并通过 DSMEM 交换互补半块。

SM90 · cluster size = 2 hq=128 · dqk=576 · BF16 top-k=2048 · B=128 实验 API，默认路径不变

数据路径

CTA0GMEM → reg：KV rows 0–31
GMEM → reg：CTA1 为 rows 32–63
→
同一寄存器值分发reg → 本 CTA local SMEM
reg → 对端 CTA DSMEM（st.async）
→
消费每个 CTA 的 local SMEM 获得完整 64-row KV tile；随后执行 QK / PV。

没有 local SMEM → peer SMEM 的二次读取：远端写直接以寄存器为源。

流量变化

路径baselineDSMEM crossover

Fine-grained 流水与依赖

  • 子区顺序：K0L → K1R → K0R → K1L；buffer 被 PV 释放后即可装入下一 block 的对应子区。
  • CTA0 的 QK(K0L,n+1) 等待：CTA0 local-ready + CTA1→CTA0 的 remote mbarrier。CTA1 对称。
  • CTA0 不需要等待自己的 CTA0→CTA1 写完成才消费本地数据；图中双向写同步画出，因此第二轮 QK 放在两条橙色传输结束之后。

代码与构建

  • 新增 fine-grained pipelined kernel 实例化和独立 experimental launcher；baseline launcher ABI 保持不变。
  • 新增 opt-in Python API：sparse_prefill_fwd_dsmem_crossover 与 ..._pipelined。
  • Slurm 默认增量构建仅重编两个新 kernel 实例化与 api.cpp；BUILD_MODE=full 才全量编译。
  • 作业使用 --gpu-bind=map_gpu:1；若不是 GPU1，脚本在编译前退出。

这页描述的是实验实现与数据流，不代表最终性能结论；DSMEM 吞吐和端到端收益仍需以 GPU1 上的 benchmark / NCU 结果为准。

带宽模型：加载开销下界

令 BG 为该 workload 实测的有效 GMEM/HBM 聚合带宽，BL 为 local-SMEM 聚合写带宽，bD 为单方向 DSMEM 有效带宽。两条 DSMEM 方向并发，因此各自承担 144 MiB。

版本加载时间模型（不含 QK/PV）含义
baselineTbase ≈ 576 MiB / BG两 CTA 各从 GMEM 读取完整 KV 副本。
crossover，保守串行估计288/BG + 288/BL + 144/bD先读，再写 local SMEM 与对端 DSMEM；双向 DSMEM 写并发。
fine-grained，稳态下界max(288/BG, 288/BL, 144/bD)子区加载、DSMEM 写与前一 block 计算重叠；仍有首尾与 mbarrier 开销。
  • 以 H100 SXM 的 3.35 TB/s HBM 峰值作理想上界：baseline 的 GMEM 下界约 576 MiB / 3.35 TB/s = 0.180 ms；crossover 的 GMEM 部分约 0.090 ms。
  • 若要不让 DSMEM 延长这 0.090 ms 的稳态窗口，每个方向需约 144 MiB / 0.090 ms ≈ 1.68 TB/s 的有效 DSMEM 带宽；等价于 HBM 带宽的一半。
  • GMEM→reg 与 GMEM→local SMEM 共享同一 HBM/L2 通路，不能把二者带宽相加。实际值应以 NCU / microbenchmark 的有效带宽代入，不能直接用峰值替代。
