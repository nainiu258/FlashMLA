# SM90 sparse-prefill SASS: WG0/WG1 consumer parallelism

Input report: `mla_sp_128x64k_sq128_skv65536_topk2048_hq128_dqk576_5321.ncu-rep`.
The full Nsight Compute SASS/source-counter export is in the sibling file
`mla_sp_128x64k_sq128_skv65536_topk2048_hq128_dqk576_5321.sass_ncu_source.txt`.
It contains 3,917 lines, with the static SASS PC, instruction, and the
collected source counters.

## Result

The two consumers are independent 128-thread warpgroups in one 384-thread
CTA. They do not execute the same HGMMA instruction in lockstep. NVCC emits
separate SASS regions for their QK and PV work, each with its own accumulator
register range (`R152` for QK/P and `R24` for PV/O). Hopper schedules their
four constituent warps independently; asynchronous HGMMA allows one
warpgroup to enqueue a GMMA batch while another runs scalar code, waits for
K/V, or enqueues its own batch.

The pair is only synchronized at four 256-participant named barriers. The
producer warpgroup is not a participant in these barriers.

```text
WG0: QK(K0) -> softmax(P0) -> B0 arrive -> PV(P0,V0L)
                                       -> B1 wait -> publish S0 -> B2 arrive
                                       -> B3 wait -> PV(S1,V1L) -> QK(K0,next)

WG1: QK(K1) -> B0 wait -> softmax(P1) -> B1 arrive -> PV(P1,V1R)
                                       -> publish S1 -> B2 wait -> PV(S0,V0R)
                                       -> B3 arrive
```

This is temporal overlap, not a guarantee that two HGMMA instructions issue
in one cycle: the groups share the SM tensor-core pipe. It gives the warp
scheduler another ready warpgroup while its peer has an outstanding GMMA,
load, or synchronization dependency.

## SASS evidence

The static PCs below are in the exported file. PC addresses are process-load
addresses and can vary between runs; the opcode and ordering are the stable
identifiers.

| Role | SASS evidence | Meaning |
|---|---|---|
| WG1 QK | `HGMMA.64x64x16.F32.BF16 R152, ...` beginning at `0x70e44d6421b0`; `WARPGROUP.DEPBAR.LE gsb0, 0x0` at `0x70e44d643140` | QK accumulator is `rP1` in registers. The `DEPBAR` is the local `warpgroup_wait`, not a wait on WG0. |
| WG1 local/remote PV | HGMMA `64x256x16` at `0x70e44d644970` and `0x70e44d644b40` | First consumes register `rS1`; second consumes shared `S0`. |
| WG0 local PV | HGMMA `64x256x16` at `0x70e44d649fe0` | Consumes register `rS0` and `V0L`. |
| WG0 remote PV | HGMMA `64x256x16` at `0x70e44d64b2f0` | Consumes shared `S1` and `V1L`. |
| WG0 next QK | recurring `HGMMA.64x64x16` sequence beginning at `0x70e44d64b560` | Starts the next K0 QK computation after the current PV/data-exchange sequence. |
| producer-to-consumer hand-off | `SYNCS.PHASECHK.TRANS64...` and `SYNCS.ARRIVE.TRANS64...` | Hardware mbarriers for independently loaded K0/K1 pieces. |

`WARPGROUP.ARRIVE` immediately ahead of HGMMA batches is the compiled
`warpgroup_commit_batch()` sequence. `WARPGROUP.DEPBAR.LE gsb0, N` is the
compiled `warpgroup_wait<N>()`; hence an HGMMA batch can remain outstanding
while another eligible warpgroup is scheduled.

## Cross-consumer synchronization

The SASS named-barrier count is `0x100 = 256` threads, exactly WG0 + WG1
(`128 + 128`), which proves these are consumer-only rendezvous points.

| Protocol | WG0 instruction | WG1 instruction | Data dependency |
|---|---|---|---|
| B0 / `wg0_bunch_0_ready` | `BAR.ARV 0x8, 0x100` at `0x70e44d649fc0` | `BAR.SYNC.DEFER_BLOCKING 0x8, 0x100` at `0x70e44d643210` | WG0's P0 softmax state permits WG1's P1 softmax update. |
| B1 / `wg1_bunch_0_ready` | `BAR.SYNC.DEFER_BLOCKING 0x9, 0x100` at `0x70e44d64a100` | `BAR.ARV 0x9, 0x100` at `0x70e44d644770` | WG1 publishes the updated max/scale back to WG0. |
| B2 / `wg0_s0_ready` | `BAR.ARV 0xa, 0x100` at `0x70e44d64b140` | `BAR.SYNC.DEFER_BLOCKING 0xa, 0x100` at `0x70e44d644b10` | WG0 has written S0; WG1 can issue `S0 x V0R`. |
| B3 / `wg1_s1_ready` | `BAR.SYNC.DEFER_BLOCKING 0xb, 0x100` at `0x70e44d64b170` | `BAR.ARV 0xb, 0x100` at `0x70e44d644cd0` | WG1 has written S1; WG0 can issue `S1 x V1L`. |

The mapping agrees with `csrc/sm90/prefill/sparse/phase1.cuh`: WG0 is at
lines 318--372 and WG1 is at lines 380--437.

## Profile-count sanity check

The launch has 256 CTAs and `topk=2048`, so the pair loop has
`2048 / (2 * 64) = 16` iterations. The recurring WG1 QK HGMMA PCs report
`524288` thread instructions:

```text
256 CTAs * 16 pair iterations * 128 threads/WG = 524288
```

This is exactly one consumer warpgroup at a time, not `256 * 16 * 384` CTA
threads. Recurring WG0 next-QK PCs report `491520` thread instructions:

```text
256 * 15 steady-state iterations * 128 = 491520
```

The missing iteration is the separately emitted first-iteration prologue.

## What limits the overlap in this run

Nsight Compute reports an average of 2.92 active warps and only 0.42 eligible
warps per scheduler. The three warpgroups of this 384-thread CTA correspond
to three warps per scheduler, so all roles are resident, but dependencies
often leave none ready to issue. The main reported stall-pressure metrics are:

| Stall | average stalled warps per issued instruction |
|---|---:|
| long scoreboard | 3.39 |
| named/memory barrier | 1.31 |
| wait | 1.09 |
| GMMA | 0.62 |

Thus the consumer split does hide some latency, but the residual bottleneck
is primarily KV/load readiness and synchronization rather than lack of a
second consumer instruction stream.

These values are *not* the cycle latency of one barrier. The report has
`1658` PC-sampling observations classified as `barrier` at a sampling period
of `2048` cycles, which can identify barrier-related hotspots but cannot
recover the arrival-to-release duration of an individual B0--B3 instance.
